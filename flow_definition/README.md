# NiFi flow definitions

The flow that runs inside NiFi and pushes metrics to Splunk's HEC. Only
needed for the push path — when Splunk cannot reach NiFi's REST API. If it
can, use the TA's modular input instead and skip all of this.

```
nifi-1.x/   for NiFi 1.16 – 1.28
nifi-2.x/   for NiFi 2.0 and later, generated by migrate_to_nifi2.py
```

## Which one to import

| Your NiFi | Import |
|---|---|
| 1.x | `nifi-1.x/NiFiMonitoring.json` |
| 2.x | `nifi-2.x/NiFiMonitoring.json` |

Do not import the 1.x flow into NiFi 2.x. It loads, which is the problem:
five processors come up invalid and — worse — the six variables it relied on
silently disappear, leaving processors that validate cleanly while holding
`${splunk_hec}` references that resolve to nothing. They fail at runtime with
nothing to show at import time.

`nifi-1.x/NifiMonitoringTemplate.xml` is the old XML template. NiFi 2.x
removed template support entirely; it is kept only for 1.x instances that
still use it.

## After importing

Both flows ship with their environment settings blank, so nothing carries
another installation's addresses or credentials. Fill them in before
starting the flow:

| 1.x variable / 2.x parameter | What it is |
|---|---|
| `splunk_hec` | `http://your-splunk:8088`. Defaults to `http://splunk:8088`, the hostname `tests/docker-compose.yml` uses, so the flow works against the local test stack unchanged |
| `splunk_hec_token` | the HEC token (a sensitive parameter in 2.x) |
| `nifi_api_url` | this instance's API, e.g. `http://localhost:8080/nifi-api` |
| `nifi_path` | NiFi's install directory, for the log tail |
| `processors_list` | ids of the processors to track, newline separated |
| `process_groups_list` | ids of the process groups to track |

On 2.x these live in the **NiFi Monitoring** parameter context, which the
import creates. Each one carries a description that NiFi shows in the UI, so
what to fill in is visible where you fill it in rather than only here. Two `GenerateFlowFile` processors stay invalid until
`processors_list` and `process_groups_list` have values — that is
deliberate. NiFi refuses to start a processor with an empty required
property, which is a better outcome than starting one pointed at ids from
somebody else's instance.

## Regenerating the 2.x flow

```
python3 migrate_to_nifi2.py nifi-1.x/NiFiMonitoring.json nifi-2.x/NiFiMonitoring.json
```

The 2.x flow is generated, not maintained by hand: the definition is 6000+
lines of machine-written JSON, so a reviewable script beats an untraceable
edit. Change the 1.x flow, re-run, re-import.

### What the migration does, and how it was established

Every item was found by importing into a real NiFi 2.11.0 and reading the
validation state back — not from the migration guide.

| Change | Why |
|---|---|
| `GetHTTP` ×3 → `InvokeHTTP` | removed in 2.0 |
| Property names for those three | `URL` → `HTTP URL`, `Data Timeout` → `Socket Read Timeout`, `User Agent` → `Request User-Agent`, `Follow Redirects` → `Response Redirects Enabled` |
| `false` → `False` on those booleans | 2.x allows only `True`/`False`; lowercase is rejected |
| Connections out of them: `success` → `Response` | InvokeHTTP has no `success` relationship |
| `Original`, `Failure`, `Retry`, `No Retry` auto-terminated | InvokeHTTP has five relationships where GetHTTP had one |
| `JoltTransformJSON` ×2 relocated | `processors.standard` → `processors.jolt`, `nifi-standard-nar` → `nifi-jolt-nar` |
| Its properties renamed | `jolt-spec` → `Jolt Specification`, `jolt-transform` → `Jolt Transform`, `pretty_print` → `Pretty Print` |
| Variables → parameter context | the Variable Registry was removed in 2.0 |
| `${var}` → `#{var}` everywhere | parameter reference syntax |
| Parameter context set on **every** group | a child group does not inherit its parent's context; setting it only on the root left every subgroup broken |
| `Authorization` declared a sensitive dynamic property | a non-sensitive property cannot reference a sensitive parameter, and this keeps the token out of an exported flow |

Deliberately **not** changed: the existing `InvokeHTTP` processors' property
names. NiFi 2.x migrates those itself on import (`Remote URL` → `HTTP URL`,
value intact).

### Verified result

Importing `nifi-2.x/NiFiMonitoring.json` into NiFi 2.11.0: 39 processors,
37 valid. The two that are not are the `GenerateFlowFile` pair above; giving
`processors_list` and `process_groups_list` any value takes it to 39 of 39.
